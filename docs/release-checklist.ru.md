# Единый release checklist (Entware feed, 2026-11-20)

Обязательный порядок проверок для любого изменения production-канала (`latest`-фид и релизы entware-go). Каждая строка — либо фактическая команда, либо явное решение. Статусы отчёта используются только честные: **PASS** (есть воспроизводимое доказательство), **BLOCKED** (классифицированный блокер), **NOT_TESTED** (не проводилось). Запрещено создавать релизные заявления шире реальных доказательств; `SKIPPED` не считается `PASS`.

## 0. Перед началом: границы полномочий

- Без отдельного owner GO: не изменять release metadata (включая `make_latest`), не трогать живые роутеры, не публиковать beta/stable каналы, не делать force-push, не удалять «чужие» исправные пакеты из `latest`.
- Все изменения — через Draft PR + зелёный CI + явный GO перед merge/publish (см. раздел 10).

## 1. Теги и latest metadata (два разных эндпоинта)

- Явный тег-фид: `gh api repos/<repo>/releases/tags/latest` — проверяемые активы.
- Указатель «последнего релиза»: `gh api repos/<repo>/releases/latest` — GitHub без явного закрепления выбирает его **не по тегу и не по semver**, а среди опубликованных не-prerelease релизов по дате создания (issue #71). Более новый архив отката может перехватить этот указатель, не изменяя фид; закрепление через `make_latest=true` предотвращает такой сценарий.
- Read-only диагностика: `GH_REPO=<repo> python3 scripts/publish_ipks.py --check-latest` — exit 0 только если указатель указывает на релиз тега `latest`. **Диагностика отделена от штатной публикации, очистки и verify-only**: ошибка или недоступность неявного `/releases/latest` не должна блокировать проверенные операции с явным тегом `latest` (PR #72).
- Если указатель похищен: ремонт — два one-off PATCH `make_latest` (предварительные проверки, команды, откат и post-verification — в issue #71), только по owner GO. Тег, активы и история не меняются.
- Все внутренние ссылки на релизы — только по явному тегу (`releases/download/<tag>/<file>`, `gh release upload/download latest`); `/releases/latest/download/...` во внутренних скриптах и документах запрещён (проверять grep'ом).

## 2. Upstream-версии и SDK

- Версия пакета берётся из upstream-тега (check-version workflow валидирует формат `X.Y.Z`), `PKG_RELEASE` — **только** из `Makefile` пакета; bump `PKG_RELEASE` без нового upstream-тега обязан приводить к пересборке (revision-aware план: `--plan --expected-release "$RELEASE"`).
- SDK: соответствие версии Go в SDK требованиям go.mod upstream (гейт в build-mihomo.yml); не смешивать артефакты разных SDK.

## 3. Полный комплект IPK

- Все ожидаемые варианты присутствуют (`expected_variants` в publish_ipks.py: для mihomo — 5 архитектур + nohf).
- Один и тот же (X.Y.Z-N) на всех вариантах; имена канонические (`mihomo_nohf_*` для nohf).

## 4. SHA256

- Обязательная сверка **полного SHA256** скачанных IPK с GitHub digest-леджером (`asset.digest == sha256:<hex>`) и независимо вычисленным `sha256sum`. Если релиз содержит `SHA256SUMS.txt`, дополнительно проверить и его. В rolling-релизе `latest` на 20.11.2026 такого манифеста нет (12 IPK); в архиве отката `mihomo-1.19.34-2` манифест есть. Не считать отсутствие необязательного файла ошибкой публикации.
- Критично: **не атрибутировать аппаратный тест одного комплекта байтами другого** — LAB-репак и SDK-сборка одного номера имеют разные SHA256; доказательства действуют только на свой комплект.

## 5. Init-скрипты и opkg-владение

- Пакет несёт ровно один init своего поколения (mihomo `-3` → `S28mihomo`, `-2` → `S99mihomo`); пакетного файла чужого поколения в IPK нет.
- Init — файл из data.tar пакета (owned → opkg удаляет при upgrade), mode 0755.
- Нет параллельного init'а предыдущего поколения, оставленного пакетом.
- KAS-компоненты: watchdog resolvит init по дайджесту blob'а и отказывается при ambiguous/симлинках; uninstaller inventory знает оба имени (S28/S99). Старые тела watchdog (до S28-резолвера) самообновляются из канала.

## 6. Conffiles и пользовательский конфиг

- Пользовательский конфиг объявлен conffile (`/opt/etc/mihomo/config.yaml`), mode 0600 у поставляемого семпла.
- opkg сохраняет пользовательский конфиг при upgrade/downgrade и кладёт новую версию как `*.opkg`; миграция `-2`→`-3`→`-2` не теряет настройки.

## 7. Совместимость архитектур

- Реальный ELF/ABI против имени варианта: class, e_machine, EI_DATA (endian!) и e_type читаются **в эндianности файла** (big-endian MIPS `e_type/e_machine` при little-endian чтении даёт мусор — 512/2048 вместо 2/8; две ловушки уже ловили).
- fp_abi/softfloat для MIPSel-3.4; отсутствие динамики и чужих интерпретаторов там, где контракт статической сборки.
- UPX: паковка подтверждается маркером `UPX!` и целостностью распаковки; слепо UPX-ить все архитектуры запрещено.

## 8. Откат

- Архивный релиз отката существует и полон (все варианты + SHA256SUMS) **до** очистки старых активов из фида.
- Инструкции отката опубликованы (для mihomo: `opkg install --force-downgrade` из архивного релиза mihomo-1.19.34-2; физический откат на KN-1913 — NOT_TESTED, честно помечен).

## 9. Публикация: сначала проверка, потом удаление

- Публикация новым комплектом идёт `publish(keep_old=True)` → отдельный `--prune-only`; удаление старых активов только после верификации полного нового набора (механика publish_ipks.py, concurrency group `entware-latest-publication`).
- Scope-фильтр: prune трогает только активы своего пакета (`package_` префикс) — чужие пакеты (beszel, telemt, panel, warpscout) целы; сверять список и digest'ы до/после.
- Повторные сборки без изменения версии/ревизии не происходят (план `update=false`, `prune=false`).

## 10. Приёмка изменений в основную ветку

- Ветку `gh-action-build` меняет только merge-commit подтверждённого PR (Draft → CI зелёный → review → owner GO → merge); без force-push и переписывания истории.
- Перед merge: upstream-тег не изменился с момента проверки, CI на merge-результате зелёный, merge-diff просмотрен, набор релизов согласован заранее.
- Beta-каналы (TeleMT MIPSel и т.п.) публикуются только отдельными prerelease с GO-флагом-маркером и никогда не пишут в `latest`; сборка кандидатов — только в artifacts (workflow «no release»).

## 11. Документация после релиза

- Статусы в документах сверены с фактическими прогонами (ссылки на run-id); устаревшие заявления (например, «указатель latest = фид» без проверки) исправляются с датой.
- Матрица консолидации веток/PR актуальна (канонические реализации, superseded-решения с указанием, куда перенесена работа).
